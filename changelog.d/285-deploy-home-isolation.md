修復 deploy 測試逃逸 HOME 隔離寫進真實 host，以及 `start.sh` 劫持他人 cortex instance（#285）。**問題 A**：`paths.home_root()` 原本是裸的 `Path.home()`，是 facade 中唯一沒有 `PSC_*` 覆寫點的 root，且 deploy CLI 無 `--home-dir` 參數——隔離百分之百依賴呼叫端自己記得換 `HOME`，漏一次就直接寫進真實家目錄（現場實際產生了三平面共 9 個 `demo-agent` 檔案，systemd unit 內燒著測試 fixture 專用的 `/srv/paulshaclaw`）。修法：`home_root()` 加 `PSC_HOME_ROOT` 覆寫（仿 `repo_root()` 慣例）、五個 deploy 子命令加 `--home-dir`、`tests/conftest.py` 以 session autouse fixture 把 `PSC_HOME_ROOT` 導向 pytest tmp 作為第二道防線（各 stage7 測試的 `deploy_env()` 同步顯式覆寫回自己的假 HOME，否則 subprocess 會繼承 conftest 的 tmp 而讓斷言找不到檔案）；新增反例測試 `tests/test_home_isolation.py`——其 CLI 案例刻意把 `HOME` 導向誘餌 tmp 而非保留真實值，這樣 `--home-dir` 失效時檔案落在誘餌、斷言照樣抓得到，但不會重演事故本身。**問題 B**：`scripts/start.sh` 的 `cortex_instance()` 預設 `cortex`，而 cortex 的 `install service` 會就地覆寫 `<instance>-manager.env` 的 managed keys（含 `PSC_REPO_ROOT`／`PY`）——同時裝了兩個 repo 的機器上會劫持對方的 instance，症狀是 cortex 所有 work-action 掛住且潛伏到下次重啟才爆。改為覆寫前檢查：既有 env 的 `PSC_REPO_ROOT` 指向別的 repo 時跳過 install service、印警告、改走 local fallback 並繼續啟動（不中止，沿用 #277 精神）；不改預設 instance 名，因為那會讓機器上同時存在兩個 manager。**順帶**：`restore_core_from_checkpoint()` 繞過 create-only 判準一事裁決為刻意例外（rollback 還原的是使用者自己在 checkpoint 當下的內容，不是模板 placeholder），於 docstring 與 release-contract §8.4 明確記錄並由測試守住；`ApplyInstallPlanCreateOnlyTests` 的 `if True:` 補回 `try/finally` 清理；`.test-artifacts/` 加入 `.gitignore` 並移出版控（該批測試產物於 #125 遷移刀誤入 repo，導致每次跑測試 git status 都髒）。真實家目錄的殘留產物清理指令記於 release-contract §8.8，**本 repo 不自動刪除使用者任何檔案**。
